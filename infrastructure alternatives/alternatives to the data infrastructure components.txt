The finalized tech stack for the desktop AI assistant app, designed to handle "cartridge" (.ocar) files and auto-generate "Chameleon" UI displays, is built on a high-performance **Hybrid V1 Architecture**. This stack prioritizes a lightweight footprint (~158 MB to 235 MB installed) and uses local-first processing combined with cloud intelligence.

### 1. App Shell & Frontend (The Interface)
The app uses a "3-column" layout (Sidebar, Center Workspace, Right Copilot) and is designed to morph its UI based on the active cartridge's requirements.
*   **Application Shell:** **Tauri v2** (Rust-based). It was chosen over Electron for its significantly smaller binary size and native OS performance.
*   **Frontend Framework:** **React + TypeScript**.
*   **UI Components:** **Shadcn/UI** and **Tailwind CSS**. These provide high-fidelity Radix UI primitives for a "Spotify-level" aesthetic.
*   **Auto-Generation Logic:** **"Chameleon UI" (Schema-Driven UI)**. The frontend uses a **Validation Layer (Zod)** to parse the `manifest.yaml` inside a cartridge and deterministically map its keys to pre-built React components (e.g., toggles, sliders, file pickers).
*   **State Management:** **TanStack Query** (for data fetching) and **Zustand** (for global UI state/mode toggling).

### 2. Backend Logic Layer (The Sidecar)
Because Tauri cannot run Node.js natively, the app utilizes the **Sidecar Pattern**.
*   **Sidecar Runtime:** **Node.js Runtime** (bundled as a standalone executable). This process orchestrates the agents and handles local logic.
*   **Agent Engine:** **Claude Code CLI**. This replaces OpenCode as the core "brain" logic to save months of development time, as it natively handles file reading, command execution, and tool searching.
*   **Execution Loop:** **"Ralph Driver"**. A Node.js script that manages the **Ralph Wiggum state loop**, driving the Claude CLI in "one-shot" mode while persisting progress in a `PRD.json` file inside the cartridge.

### 3. Intelligence & AI Pipeline
The system uses a "Local First, Cloud Second" strategy to balance cost and accuracy.
*   **Primary Reasoning Brain:** **Gemini 1.5 Flash/Pro** (via API) or **Claude 3.5 Sonnet**. Users typically "Bring Your Own Key" (BYOK) to maintain a free tier for the developer.
*   **Local AI Engine:** **ONNX Runtime**. This is used to run quantized local models (embeddings, OCR) without a Python backend.
*   **Vision/OCR:** **RapidOCR (PP-OCRv4)**. A lightweight (~16 MB) engine used for reading PDFs, screenshots, and browser content.
*   **Web Automation:** **Model Context Protocol (MCP)** with **dev-browser**. This allows the assistant to connect to the user’s already-open Chrome browser using the Chrome DevTools Protocol (CDP).

### 4. Data & Memory Layer (The "Diet Graph")
The app manages local data efficiently to allow searching through massive personal archives.
*   **Structured Metadata:** **DuckDB**. Used for fast SQL filtering and managing cold metadata.
*   **Vector Database:** **LanceDB (Native)**. A serverless, disk-based vector store for semantic retrieval that does not bloat RAM.
*   **Embedding Model:** **bge-micro-v2** or **all-MiniLM-L6-v2** (Quantized to INT8). These tiny models (~25 MB) convert text into searchable vectors locally.
*   **Re-Ranker:** **jina-reranker-v1-tiny-en**. A high-performance, sub-40MB model used to ensure search quality.

### 5. Cartridge Structure (.ocar)
Each cartridge is a ZIP bundle organized for "Just-in-Time" tool loading.
*   `manifest.yaml`: Controls the UI layout, triggers, and data scope.
*   `CLAUDE.md`: The system prompt/instructions automatically loaded by the engine.
*   `PRD.json`: The persistent memory/to-do list for long-running autonomous tasks.
*   `scripts/`: Local Python or JS "Glue Scripts" for specific deterministic actions.
*   `memory/`: Optional pre-indexed vector data for the specific domain.

The tech stack for **qmd** (Query Markup Documents), the highly optimized local document search engine built by Tobi Lütke, is centered around a "local-first" philosophy. It is designed to perform sophisticated Hybrid RAG (Retrieval-Augmented Generation) without requiring a central server.

The full tech stack includes the following components:

### 1. Core Runtime and Engine
*   **Node.js & `node-llama-cpp`**: The application is built on the Node.js platform. It leverages the `node-llama-cpp` library to run Large Language Models (LLMs) locally on the CPU.
*   **GGUF Model Format**: qmd utilizes quantized **GGUF** models, which allow heavy AI models to run efficiently on consumer-grade hardware with reduced RAM footprints.

### 2. Database and Storage Architecture
The system uses a "single-file" architecture where a single database handles both relational data and mathematical vectors.
*   **Primary Database**: **SQLite** (specifically a `qmd.db` file).
*   **Vector Search Extension**: **`sqlite-vec`** (formerly `sqlite-vss`), which enables the storage and querying of high-dimensional embeddings directly within SQLite.
*   **Full-Text Search (FTS)**: **FTS5**, an internal SQLite extension used to perform high-speed keyword (BM25) searches.

### 3. AI Models (Standard and SOTA Options)
qmd requires three specialized models running in parallel for its hybrid pipeline:
*   **Embedding Model**: Traditionally uses **`nomic-embed-text-v1.5`** or **`embeddinggemma-300m`** (approx. 200MB–300MB). The high-ranking **`stella_en_400M_v5`** is often cited as a State-of-the-Art (SOTA) alternative.
*   **Reranking Model**: Employs a **Cross-Encoder Reranker**, such as **`qwen3-reranker-0.6B`** or a generative model like **`Llama-3.2-1B-Instruct`**.
*   **Reasoning/Query Expansion**: Often uses a generative model to perform **HyDE** (Hypothetical Document Embeddings), where the AI "hallucinates" a perfect answer to improve search accuracy.

### 4. Search and Retrieval Methodology
The "Secret Sauce" of qmd is its **Triple-Path Retrieval** logic:
*   **`lex`**: Traditional BM25 keyword matching for exact terms.
*   **`vec`**: Standard vector similarity for semantic concepts.
*   **`hyde`**: Matching against a hypothetical AI-generated answer to bridge the "semantic gap".
*   **Fusion Logic**: Uses **Reciprocal Rank Fusion (RRF)** to merge these disparate results into a single ranked list, often applying a "Top-Rank Bonus" to prioritize winners from the keyword or vector streams.

### 5. Hardware Profile
*   **RAM Usage**: Typically requires **~2GB+ of RAM** to run the Node.js runtime alongside the quantized models in parallel.
*   **Performance**: Capable of sub-second local retrieval after an initial "build-time" indexing phase.

The finalized tech stack for the GitHub search tool (often referred to in the sources as **Repogrep**) is designed around a **"Split Brain" Search Architecture**, which separates the high-volume repository discovery phase from the deep code-level analysis. Depending on the deployment scale (Unicorn/Funded vs. $0/Show-and-Tell), the technology choices vary to optimize for either raw power or cost-efficiency.

### 1. High-Scale / Funded Architecture (10M Repos)
This stack is designed for enterprise-grade speed and depth, indexing up to 10 million repositories.

*   **Ingestion & Crawling Swarm:**
    *   **Targeting:** **Google BigQuery** (GitHub Archive) to generate the target repository list.
    *   **Orchestration:** **Go (Golang)** distributed binary using **Redis** for task queuing.
    *   **Compute Fleet:** **AWS Spot Instances** (c5.large) or **Hetzner Cloud** nodes for high-speed unzipping and parsing.
    *   **Network:** **Rotating Residential Proxies** (Smartproxy/Bright Data) to bypass GitHub rate limits.
*   **Data & Storage Layer:**
    *   **The Warehouse:** **Cloudflare R2** (preferred for zero egress fees) or **AWS S3** storing ~30TB of raw code.
    *   **Discovery Layer (Fast Search):** **Typesense** hosted on **Hetzner Dedicated RAM Servers** (128GB–512GB RAM) for sub-20ms keyword and metadata search.
    *   **Vector Core:** **LanceDB** for high-performance vector storage and **LEANN** (LLM-Enhanced Approximate Nearest Neighbor) for a 97% reduction in index storage costs.
*   **Intelligence & AI Pipeline:**
    *   **The "Summarizer" (Ingestion):** **RunPod Serverless** running a custom-trained **Qwen-2.5-Coder-7B** model to generate "Intent Summaries" for code functions.
    *   **Embeddings:** **Nomic-Embed-Text-v1.5** (piggybacking on the same GPU as Qwen) to generate vectors.
    *   **The Auditor (Search):** **DeepSeek-V3 API** for final high-level code audits and answering complex user queries.

### 2. $0 / Show-and-Tell Architecture (800k Repos)
This "Garage Startup" stack focuses on bypassing all infrastructure costs by shifting compute to the user's browser.

*   **Backend & Hosting:**
    *   **API Server:** **Oracle Cloud Free Tier** (ARM Ampere A1) hosting a **Golang** backend.
    *   **Networking:** **Cloudflare Tunnels** (`cloudflared`) to expose the local API securely.
    *   **Frontend:** **Next.js** or **React** hosted on **Vercel** or **Cloudflare Pages**.
*   **Local-First Search Engine:**
    *   **Relational/Vector DB:** **LanceDB** (Disk-based) to handle 800k vectors within a 1GB RAM constraint.
    *   **The "Skeleton Map":** Storing only **File Paths** and **Exported Symbols** (function/class names) instead of full code to fit on small disks.
    *   **Embeddings:** **Transformers.js** running in the user’s browser (all-MiniLM-L6-v2) to generate vectors at $0 cost to the server.
*   **Reasoning Layer:**
    *   **"Bring Your Own Key" (BYOK):** Users provide their own **DeepSeek**, **Claude**, or **OpenAI** keys (stored in `localStorage`) to power the "Surgical JIT Loop" that fetches and analyzes code live from GitHub.

### 3. Alternative Platform Versions
*   **Desktop Version ("Heavy Metal"):** Built on **Tauri (Rust)** with a **Python Sidecar** for local AI execution and **SQLite** for persistence.
*   **MCP Server Version:** A headless **Python (FastMCP)** server that allows agents like Claude Desktop or Cursor to query the repository index programmatically.
*   **Full-Stack "Super-Brain":** Integrates **DSPy.RLM** (Recursive Language Models) for deep scanning, **Hermes-Agent** for state orchestration, and **TabPFN** for real-time Bayesian probability and alpha-factor optimization.

**DuckDB** is mentioned extensively across the sources as a high-performance, embedded, analytical database engine (**OLAP**) optimized for managing relational metadata, structured data, and large-scale analytical queries. It is frequently presented as the "Left Brain" of hybrid search architectures, complementing vector databases like LanceDB.

Below are the key contexts and systems where DuckDB is mentioned:

### 1. Role as the "Analytical Engine" and "Warehouse"
*   **The "Left Brain":** DuckDB is described as the "Left Brain" in retrieval systems, responsible for logic, precise facts, dates, categories, and analytical prompts (e.g., "how much," "count," or "average").
*   **Source of Truth:** It acts as the "Warehouse" or "Source of Truth," storing raw text, logs, transaction tables, and immutable history.
*   **OLAP Power:** DuckDB is noted for its ability to chew through 100GB+ CSV or log files in seconds due to its columnar processing, making it superior to SQLite for massive datasets.

### 2. Hybrid Search and "The Handover" Strategy
*   **Precision Filtering:** In hybrid architectures, DuckDB is used to narrow down a "haystack" (millions of documents) to a small "pile" (thousands matching specific metadata like date or user ID) before a vector database like LanceDB searches for the "needle".
*   **The Handover Pattern:** Sources describe a "Handover" workflow where DuckDB performs a complex SQL join or filter to find specific IDs, which are then passed to LanceDB for semantic search.
*   **Denormalization:** It is used in nightly ETL jobs to pre-calculate and write analytical columns directly into LanceDB tables to speed up real-time searches.

### 3. Graph Capabilities (DuckPGQ and Recursive SQL)
*   **DuckPGQ Extension:** DuckDB can be turned into a high-performance graph database using the **duckpgq** extension, allowing Cypher queries directly on SQL tables.
*   **Recursive Joins:** It can simulate knowledge graphs using recursive Common Table Expressions (CTEs) to map thematic progressions over time.
*   **LiteGraph Integration:** In some stacks, DuckDB stores the raw data while **LiteGraph** stores the "bridge nodes," with a Python bridge connecting the two.

### 4. Performance and Hardware Constraints
*   **HDD Friendliness:** On mechanical hard drives (HDD), DuckDB is preferred for its sequential scan capabilities and "Sequential-Heavy" processing.
*   **RAM Management:** While DuckDB is fast, complex queries on massive datasets can be memory-intensive ("The RAM Gambler"), risking Out-of-Memory (OOM) crashes if not managed carefully.
*   **Data Compression:** It uses Parquet-style compression, significantly shrinking raw text files (e.g., 60GB of raw data can shrink to ~15GB-30GB in DuckDB).

### 5. Specific Project Implementations
*   **LifeOS Coach:** In "v14" of this project, the stack shifted from a heavy Postgres/Redis setup to an embedded DuckDB/LanceDB stack to reduce complexity and cost.
*   **BetClaw AI:** Uses DuckDB for its analytics engine to perform instant win/loss ROI calculations on historical betting tickets.
*   **Repogrep (GitHub Search):** Utilized for high-signal search indices and metadata filtering across millions of repositories.
*   **File Indexer:** Acts as the "Data Hub" for filtering archives, managing temporal gap analysis, and storing extracted entities.
